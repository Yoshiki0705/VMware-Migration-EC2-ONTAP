# ブロック性能の実測を姉妹リポジトリから受け取るときの約束

このプロジェクトの検証項目「FSx for ONTAP iSCSI の IOPS / スループット実測」は、測定環境を
二重に作らず [S3-Burst-on-ONTAP-Files](https://github.com/Yoshiki0705/S3-Burst-on-ONTAP-Files)
の perf-matrix の結果を参照する方針にした。**このファイルは、その結果が来たときに何をしてよくて
何をしてはいけないかの記録である。** 数値が来る前に書いてあるのは、来てから思い出す形にすると
誤用するため。

## 現在の状態（2026-09-13 更新）

| ID | 内容 | 状態 |
|---|---|---|
| F-1 | iSCSI（LUN、raw device）、TCP 1 / 2 / 16 | **実施済み（2026-09-12）** |
| F-2 | NVMe/TCP（namespace、raw device）、F-1 と同条件 | **実施済み（2026-09-13）** |
| F-3 | 速かった側でキャッシュ常駐 / 非常駐 | **実施済み（2026-09-13、3 回）** |

**3 つとも実施済みで、先方の測定環境は撤去済み。** 追加の測定を依頼できる状態ではない。

**セッション数の定義が変わった。** 計画時は「1 と 8」だったが、実測では**指定値ではなく数えた
TCP の本数**（1 / 2 / 16）で記録されている。`nr_sessions=1` でも両ポータルへログインすると 2 本に
なるため。

### F-1 で分かったこと

**「必要帯域 ÷ 625 MBps = セッション数」は成立しない。両方向に外れる。**

| 数えた TCP | 1 MiB 逐次読み | 除数からの予想 | 実測 ÷ 予想 |
|---|---|---|---|
| 1 | 1,135.18 MB/s | 625 MB/s | 1.82 倍 |
| 2 | 1,135.18 MB/s | 1,250 MB/s | 0.91 倍 |
| 16 | 1,970.43 MB/s | 10,000 MB/s | 0.20 倍 |

**1 本から 2 本では逐次スループットが 1 バイトも動かない。** 上限は 1 フローの容量ではない。
動くのは 2 本から 16 本に増えたときだけ。4 KiB ランダムは読み 41,256 → 125,629 IOPS、
書き 76,754 → 186,462 IOPS。

**1,135 MB/s は 9.08 Gbps で、5 Gbps という documented の記述の約 2 倍。** 先方は原因を
確認していないため書いていない。**こちらも原因を書かない。**

## 引用してはいけない読み方

先方が挙げた 3 点と、先方が後から足した 4 点目。**4 つとも先方の実測または設計に基づく。**

**窓が 300 秒なのでベースラインとして引用しない。** 同じ環境で 1,536 MBps 構成の読みが 27 分かけて
2,882 → 1,439 MB/s へ落ちるのを先方が実測している。300 秒の値はバーストを含む。

**raw device の値なので、ファイルシステムを載せた場合の値ではない。** このプロジェクトの用途は
移行後のデータ領域（LUN の上にファイルシステムを作って `fstab` でマウント）なので、
**そのままでは「移行後のボリュームが出す値」として引用できない。** 「同一条件での上限の目安」
としてのみ引用する。

**NFS / SMB と同じ表に置かない。** 理由は 2 つあり、どちらも先方の実測。データ LIF が別ノードの
別ポートに載っていること、raw device にファイルシステム層が無いこと。

**スループット容量が違えば上限そのものが違う。** 先方の構成は 6,144 MBps・SSD 4,096 GiB・
プロビジョンド 200,000 IOPS。**引用時に先方の構成値を併記する。** こちらの移行先が別の容量なら
「同一条件」が成立しない。

**プロトコル間の倍率を引用しない。理由は 2026-09-15 の 2 回の測り直しで 3 つに増えた。**
1. **1 接続の値はプロトコルではなくデプロイで決まる。** 同一ファイルシステムでは 1,135.19 対 1,135.88（0.06% 差）、別デプロイでは iSCSI 1 セッションも NVMe も 591 台。**9.08 Gbps と 4.73 Gbps の 2 つの位置に出て、デプロイ内では 0.01 MB/s 以内に安定する。**
2. **ANA の経路が逐次読みに 1.33 倍を作る。** 同一デプロイ・同一 `connect-all` で 2,366.59 対 1,774.77。**デバイス番号は経路を表さない**（探索順で決まる）。**公開済みの 1.84 倍のうち、経路で説明できたのはこの分だけで、残りは未確認。**
3. **構成で順序が入れ替わる。** iSCSI 16 セッションが 4,025.39、NVMe の `connect-all` は交渉されたキューが実効 4 で止まり 2,366。
**公開済みの組から読める 1.92 倍はプロトコルの性質ではなかった。** 1 組から出る倍率を定数として引かない。引用してよいのは「どの手順で・どの形状の I/O を測ったかで順序が入れ替わる」という質的な結論まで。

**「iSCSI は環境間で安定」と書かない。** 3 モードとも 1 デプロイでの実測だったが、2026-09-15 に 2 デプロイ目で 1 セッション 1,135.19 / 両ポータル 1,135.18 が出た。**証拠が無いという状態ではなくなったが、2 点は分布ではない**（multi は依然 1 デプロイのみ）。**プロトコル選択の根拠には使わない。**

**ANA が無いことは「AL2023 では」と言える範囲に広がった（2026-09-15）。** 先方が**カーネル 3 系統（6.1.186 / 6.12.103 / 6.18.48）すべてで `CONFIG_NVME_MULTIPATH` が未設定**であることを、ファイルシステムを作る前にリポジトリのカーネルパッケージから確認した。**以前の限定（2 日間に返された AMI に限る）は外れた。** ただし **ANA を有効にしたときの値は未測定**で、測るには別のディストロが要る（AWS の NVMe/TCP 手順は RHEL 9.3 前提）。
自環境については `grep -i NVME_MULTIPATH /boot/config-$(uname -r)` を 1 回読めば確定するが、**このプロジェクトの検証環境は撤去済みで未実施。** 先方が 3 系統で確認したので、AL2023 を使う限りこの確認の結論は変わらない見込みだが、**それは先方の観測であってこちらの実測ではない。**

## 2 方向のゲートと、ブロックの扱い

**失敗の原因が方向によって違う。**

| 方向 | 何を検査するか | 失敗の原因 | 読む先 |
|---|---|---|---|
| `incoming-probes` | **姉妹がこちらから引いた文**が、こちらの編集で消えていないか | **目の前の diff** | 姉妹の contract は `origin/main`、こちらのファイルは**作業ツリー** |
| `outgoing-probes` | こちらが引いた主張が、姉妹側で言い換えられていないか | 相手の編集 | 姉妹のファイルは `origin/main` |

**incoming で読む先が非対称なのは意図的。** 登録は公開されたものだけを約束として扱い（相手の
作業ツリーにしかない登録に縛られない）、こちらは編集中の状態を見る（コミット前に気づくため）。

**ブロックしているのは `incoming` だけ。** `outgoing` は週 1 回の
[`cited-claims.yml`](../../.github/workflows/cited-claims.yml) に移した。

**この判断は前提を機械が数え直したときに変わった。** ブロックにしていた理由は「登録が多くの
ファイルに薄く散っているので、他者起因の赤は 1〜2 件で来る」だったが、
`make outgoing-probes` が出す形は `22 registration(s) across 4 file(s), 13 in the largest` で、
**6 割が 1 ファイル（`perf-matrix-results.md`）に集まっている。** 相手がそのファイルを 1 回
書き換えると、無関係な変更が 13 件の赤とともに止まる。**姉妹が先に指摘していた「赤を無視する
習慣がつく」形そのもので、こちらの前提は成立していなかった。**

**前提の数値はこのファイルに書かない。** 毎回チェッカーが再計算して出す。
**手で書いた前提は古くなり、成立しなくなった前提が判断を正当化し続ける** — 実際にこのファイルは
一度それをやって、姉妹には「18 行が 6 ファイル」と伝えていた（正しくは 4 ファイル、最大 13 行）。
形が薄く散る側に戻ったら、ブロックへ戻す判断もありうる。

**多重一致は両方向で弱い probe として報告する。失敗にはしない。**
文字列が 2 回以上あると、1 か所だけ言い換えてもゲートは緑のまま通る。**理由は方向で違う。**

| 方向 | 失敗にしない理由 |
|---|---|
| `incoming` | **文字列を選んだのは相手**なので、相手が取った判断でこちらを赤くするのは筋が違う |
| `outgoing` | 選んだのはこちらだが、**主張自体は解決している。** 「撤回された」と「アンカーが脆い」を同じ赤で出すと、必要な行動が違うのに区別できない |

現に `承認を得て実行` は 3 回あり、incoming 側で毎回報告が出る。**手で数えていたことをゲートに
移した**もので、`倍率を書かない` と `作成後の変更は ONTAP が拒否する` は手で数えて見つけていた。
**人が覚えていたから成立していた検査は、覚えなくなった時点で無くなる。**

境界のテスト（1 回なら報告しない）は、検出を外しても通ったままになるように書いてある。
**両方が落ちるなら、その対は「何かを印字した」ことしか証明しない。**

## 数値を引用するときに必要な手続き

**先方の repo は申告制の probe で言い換え事故を防いでいる**（`make outgoing-probes` /
`incoming-probes`）。数値や主張を**転記**する場合は、引用する文を 1 行渡して先方の
`docs/agent/cross-repo-probe-contract.txt` に登録してもらう。

**単なるリンクには probe を登録しない。** 先方の contract の但し書きに「主張を転記していない
see-also のリンクに probe を登録すると、依存していない文言を凍結させることになる」とある。
現在このプロジェクトが持っているのはリンクだけなので、登録は無い。

登録が必要になるのは、たとえば「除数 625 MBps に対してブロックの実測は N%」をこちらの本文に
書いた時点。**そのときに登録を忘れると、先方が言い換えた瞬間にこちらの根拠が黙って消える。**

## Adoption Playbook へ渡す 2 件（ブロック起点の移行パス）

FSx for ONTAP Adoption Playbook には**ブロック起点の移行パス**が期待されている。こちらの
費用モデルで確定した内容のうち、そのまま渡せるものが 2 件ある。

| 渡すもの | 内容 |
|---|---|
| **ブロックでは階層化を前提にできない** | `snapshot-only` はアクティブなデータを階層化せず、**SSD 使用率 50% 以下では `auto` も階層化しない**。`auto` でもランダム読みで SSD に戻る。**この 3 つで、ファイル前提の hot 比率をブロックに持ち込めない**（[出典](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/volume-storage-capacity.html)） |
| **階層化しない前提での額** | 論理 20 TiB / 512 MB/s / 5,000 IOPS で、`snapshot-only` は $3,077.63、EBS gp3 は $1,996.66。**1.54 倍高く、論理 2 PB まで逆転しない** |

**移行パスとしての含み。** オンプレでブロックだったものをファイルに置き換える経路と、
EBS + EC2 から FSx for ONTAP + EC2（あるいは他のコンピュート）へ移す経路では、
**階層化と効率化が効くかどうかが変わる。** ブロックのまま持っていくと容量単価で不利になり、
ファイルに置き換えると `auto` と効率化が効く側に入る。**費用の判断はこの置き換えを
するかどうかで分かれるので、移行パスの選択と費用の試算を切り離せない。**

こちらの `scripts/cost_comparison.py` は `--tiering-policy` と `--hot-ratio` を取るので、
両方の前提で額を出せる。

## 公開前に人が走らせる 2 つの手順

**`.private/` は gitignore なので CI に存在しない。だから下書きに効く検査は置けない。**
それでも**下書きは公開面**で、はてなに保存された時点で読者に届く。以下は手順であって
ゲートではない。**手で走らせなければ何も起きない、という弱さを持ったまま置いている。**

| 手順 | 何を見るか | 分かること |
|---|---|---|
| `make repo-names-private` | 下書きと内部ノートの GitHub リポジトリ名 | 旧名・**ローカルのディレクトリ名を書いた URL**（姉妹リポジトリはこれで 404 を 4 本作った） |
| 下記の 4 パターンを下書きに当てる | 命名・禁止製品・ベンダー中立・PII | `agent-output-audit.yml` が tracked に強制しているものと同じ規則 |

```bash
# agent-output-audit.yml と同じパターン。**規則の定義は workflow 側が持つ**ので、
# 変更したらこちらも合わせる（2 か所にあることが弱点であり、片方が古くなりうる）。

  grep -nE 'DB-I-[0-9]+|case[ #]?[0-9]{5,}|10\.[0-9]+\.[0-9]+\.[0-9]+|192\.168\.' "$f"
```
